TCP 和 UDP 是传输层（第四层）最核心的两个协议。

---

### 一、 TCP（传输控制协议）：严谨、靠谱的“完美主义者”

TCP 的核心思想是：**“宁可慢一点，也绝对不能丢掉或弄乱一个字节的数据。”**

#### 1. 面向连接 (Connection-oriented)
在传输数据之前，双方必须先建立连接。这就是著名的**“三次握手”**：
*   **客户端：** “你好，我想给你发数据，你能听到我说话吗？”（SYN）
*   **服务端：** “听到了，我也准备好接收了，你能听到我说话吗？”（SYN-ACK）
*   **客户端：** “听到了，那我们开始吧！”（ACK）

*（传输完毕后，还需要通过“四次挥手”来安全地释放连接。）*

#### 2. 可靠传输 & 有序 (Reliable & Ordered)
*   **确认应答（ACK）：** 接收方收到每个数据包后，都必须给发送方回一个“收到”的确认。如果发送方等了一阵没收到确认，就会重新发送（**超时重传**）。
*   **数据排序：** TCP 给每个数据包标上序号（Sequence Number）。如果因为网络拥堵，第 5 包比第 4 包先到，接收方会根据序号重新排好，保证应用层读到的数据顺序是 100% 正确的。

#### 3. 流量控制 (Flow Control)
*   **比喻：** 漏斗。如果发送方发得太快，接收方的缓冲区（邮箱）装不下了，数据就会溢出丢失。
*   **机制（滑动窗口）：** 接收方会在回信（ACK）中告诉发送方： “我现在的邮箱只剩 3 个空位了，你最多只能连发 3 个包。” 发送方会根据这个反馈调整发送速度。

#### 4. 拥塞控制 (Congestion Control)
*   **比喻：** 堵车。如果整条马路（互联网骨干网）都堵死了，大家还在拼命往里塞车，网络就会瘫痪。
*   **机制：** TCP 采用**“慢启动”**算法。刚开始发送时只发 1 个包，发现路况很好（能正常收到 ACK），就加倍发（2个、4个、8个）。一旦发现丢包（说明堵车了），立刻大幅度减慢发送速度，然后重新小心试探。

---

### 二、 UDP（用户数据报协议）：简单、粗暴的“速度狂人”

UDP 的核心思想是：**“我只管拼命发，收不收得到、顺序对不对，我一概不管。”**

#### 1. 无连接 (Connectionless)
不需要三次握手。UDP 就像寄明信片，写上地址直接扔进邮筒，不需要确认对方在不在家，也不需要提前和对方打招呼。

#### 2. 不可靠 (Unreliable)
没有确认机制，没有重传机制，没有排序机制。包丢了就丢了，先发的包后到也无所谓。

#### 3. 低延迟 (Low Latency) / 头部开销极小
*   **为什么快？** 没有握手延迟（直接发送），没有重传等待。
*   **头部小：** TCP 的头部为了塞下各种控制信息（序号、确认号、窗口大小），足足有 **20 字节**；而 UDP 头部非常干净，只有 **8 字节**（只记录源端口、目的端口、长度和校验和）。

---

### 三、 TCP 与 UDP 对比速查表

| 特性           | TCP                                    | UDP                                |
| :------------- | :------------------------------------- | :--------------------------------- |
| **是否连接**   | 面向连接（需三次握手）                 | 无连接（直接发送）                 |
| **传输可靠性** | 100% 可靠（不丢包、不重复、按序到达）  | 不可靠（可能丢包、可能乱序）       |
| **传输方式**   | 字节流（无边界，像自来水一样源源不断） | 数据报（有边界，一包就是一包）     |
| **速度与延迟** | 慢，延迟较高（因为有确认和重传等待）   | 极快，延迟极低                     |
| **资源消耗**   | 大（需要维护复杂的连接状态）           | 小（发完即忘，无需维护状态）       |
| **适用场景**   | 网页浏览（HTTP）、文件传输、邮件       | 视频通话、在线游戏、语音、DNS 解析 |

### 四、 这对 HTTP 意味着什么？（承上启下的关键）

理解了 TCP 和 UDP 的区别，你就能瞬间秒懂为什么 HTTP 协议要这样演进：

1.  **为什么 HTTP/1.x 和 HTTP/2 必须基于 TCP？**
    因为网页、图片、JS 脚本这些资源**容不得半点损坏**。如果一个 10MB 的网页因为 UDP 丢了 1 字节导致代码报错，整张网页可能就无法渲染。所以 HTTP 早期毫不犹豫地选择了可靠的 TCP。
2.  **为什么 HTTP/2 的多路复用在 TCP 下有瓶颈？**
    在 HTTP/2 中，所有的网页请求都挤在**一条 TCP 连接**里（多路复用）。如果其中一个数据包在路上丢了，TCP 因为要保证“可靠与有序”，会**强行暂停**后面所有包的传输，直到丢失的包重传成功（这就是 **TCP 队头阻塞**）。这就好比高速公路上有一辆车抛锚，整条单行道都被堵死。
3.  **为什么 HTTP/3 要毅然决然转投 UDP？**
    为了彻底解决 TCP 的队头阻塞，HTTP/3 把底层的 TCP 换成了 UDP。
    **但网页数据依然需要可靠传输啊，UDP 不靠谱怎么办？**
    HTTP/3 在 UDP 之上自己设计了一套协议叫 **QUIC**。QUIC 在应用层自己实现了类似 TCP 的“确认应答和重传”机制，而且它的重传是“分车道”的：1 号车道的车抛锚了，只影响 1 号车道，2、3、4 号车道依然可以超车通行。

**学习小结：**
网络协议的设计永远是在**“可靠性”**与**“性能（延迟）”**之间做权衡。TCP 选择了绝对的可靠，UDP 选择了极致的速度。而现代网络协议（如 HTTP/3 的 QUIC）正在尝试**用 UDP 的身体（速度），装上 TCP 的灵魂（应用层实现的可靠性）**。
