### 一、 HTTP 的基本特性：协议的“性格”

#### 1. 应用层协议
HTTP 负责“规定应用数据的格式”，它不关心数据怎么安全送达（那是 TCP 的事），只关心数据代表什么业务含义（如“获取网页”、“提交表单”）。

#### 2. 请求-响应（Request-Response）模型
* **机制：** “一问一答”模式。必须由**客户端**主动发起请求，**服务端**才能给予响应。
* **限制：** 服务端不能在没有请求的情况下主动向客户端推送数据（如果需要双向实时通信，后面我们会学习升级到 **WebSocket** 协议）。

#### 3. 无状态（Stateless）—— 健忘的服务器
* **含义：** **“每一次请求都是全新的陌生人。”** 服务器不保留上一次请求的任何上下文记忆。
* **例子：**
  * 请求 1：你向服务器说：“我把一双鞋放进了购物车。” 服务器答：“好，收到了。”
  * 请求 2：你又向服务器说：“我要结账。” 服务器答：“**哈？你是谁？你购物车里有什么？**”
* **解决办法：** 既然协议本身是“无状态”的，为了实现会员登录、购物车等功能，人们后来发明了 **Cookie, Session 和 Token** 等技术来辅助 HTTP “记住”状态。

### 二、 URL/URI 的结构：网络资源的定位符

日常生活中我们常说“网址”或者“链接”，但在技术上它们有严格的定义：

* **URI (Uniform Resource Identifier，统一资源标识符)**：只要能唯一标识互联网上某一个资源的，都叫 URI。
* **URL (Uniform Resource Locator，统一资源定位符)**：不仅标识资源，还告诉你**怎么找到它**（通过协议和路径）。**URL 是 URI 的子集**（所有的 URL 都是 URI，但并非所有 URI 都是 URL）。

#### 一个标准 URL 的解构：
假设你博客的完整搜索链接是：
`https://myblog.com:443/search?q=HTTP#section2`

| 组成部分                  | 示例         | 作用解释                                                     |
| :------------------------ | :----------- | :----------------------------------------------------------- |
| **协议 (Scheme)**         | `https`      | 告诉浏览器用什么方式（协议）进行通信。                       |
| **主机 (Host)**           | `myblog.com` | 服务器的域名（或 IP 地址）。                                 |
| **端口 (Port)**           | `443`        | 目标程序监听的端口。*(HTTPS 默认 443，如果是默认端口通常可以省略不写)*。 |
| **路径 (Path)**           | `/search`    | 资源在服务器上的逻辑路径（相当于找服务器上的哪个“抽屉”）。   |
| **查询字符串 (Query)**    | `q=HTTP`     | 传给服务器的参数，用 `?` 开头，多个参数用 `&` 连接。         |
| **片段标识符 (Fragment)** | `#section2`  | 浏览器内部定位锚点（比如直接滚动到网页的第二章），**这部分内容不会发送给服务器**。 |

### 三、 HTTP 请求（Request）结构

在 HTTP/1.x 中，请求报文是一个**纯文本**。你用 Socket 读出来时，它长这样：

```http
POST /search HTTP/1.1
Host: myblog.com
User-Agent: Mozilla/5.0
Content-Type: application/json
Content-Length: 12

{"q":"HTTP"}
```

我们来拆解这个报文的结构：

#### 1. 请求行（Request Line）—— 报文的第一行
包含了三个关键信息，用空格隔开：
* **方法（Method）：** 表达你想做什么。
  * `GET`：获取资源（比如看网页，**请求体通常为空**）。
  * `POST`：提交/新增数据（比如写文章、提交表单，**数据放在请求体里**）。
  * `PUT`：更新资源（整体替换）。
  * `DELETE`：删除资源。
  * `PATCH`：部分修改资源。
* **URI：** `/search`（你想访问的路径）。
* **HTTP版本：** `HTTP/1.1`。

#### 2. 请求头（Request Headers）—— 属性键值对
每一行是一个 `Key: Value`，用来向服务器传递一些控制信息和元数据：
* `Host`：目标主机名（**在 HTTP/1.1 中是唯一必须携带的请求头**）。
* `User-Agent`：浏览器的“身份证”，告诉服务器我是 Chrome 还是 Safari。
* `Accept`：告诉服务器我能接收什么类型的数据（如 `text/html`, `application/json`）。
* `Content-Type`：说明**请求体（Body）**里数据的格式（如 `application/json` 代表 JSON 数据）。
* `Content-Length`：**至关重要！** 告诉服务器请求体一共有多少字节。服务器靠它来判断数据包是否传输完毕。
* `Cookie`：浏览器自动携带的凭证，用于身份识别。
* `Authorization`：用于携带 Token（如 Bearer Token）进行安全认证。

#### 3. 空行（CRLF，即 `\r\n`）—— **分界线**
在请求头和请求体之间，**必须有一个空行**。这是协议规定的分界线，服务器看到这个空行，就知道接下来是请求体（Body）了。

#### 4. 请求体（Request Body）
用来承载要发送给服务器的数据。常见格式有：
* `application/json`：`{"q":"HTTP"}`（现代 API 最常用）。
* `application/x-www-form-urlencoded`：`q=HTTP&user=admin`（传统 HTML 表单提交格式）。
* `multipart/form-data`：用于上传文件、图片等多媒体数据。

### 四、 HTTP 响应（Response）结构

服务器收到请求处理完后，返回给浏览器的响应报文同样是纯文本：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 42
Server: Nginx

{"status":"success","result":"Found 1 article"}
```

#### 1. 状态行（Status Line）—— 第一行
* **HTTP版本：** `HTTP/1.1`。
* **状态码（Status Code）：** 比如 `200`（数字）。
* **状态消息（Reason Phrase）：** 比如 `OK`（对状态码的文本解释）。

#### 2. 状态码分类（大纲重点，建议背诵）

状态码告诉你这次请求的**最终命运**。第一位数字代表分类：

*   **1xx（信息性）：** 协议切换。
    * `101 Switching Protocols`：客户端要求升级协议（例如从 HTTP 升级到 WebSocket 长连接），服务器同意。
*   **2xx（成功）：**
    * `200 OK`：最常见的成功状态。
    * `201 Created`：POST 请求成功，且服务器创建了新资源（比如成功发布了新文章）。
    * `204 No Content`：请求成功，但响应体里**没有任何内容返回**（常见于 DELETE 操作）。
*   **3xx（重定向）：**
    * `301 Moved Permanently`：**永久重定向**。搜索引擎会把旧网址的权重转移到新网址（比如你的博客换了新域名）。
    * `302 Found`：**临时重定向**。临时跳转，旧网址依然有效（比如未登录用户访问后台，临时跳转到登录页）。
    * `304 Not Modified`：**缓存重定向**。服务器告诉浏览器：“你要的文件没变过，直接去读你的本地缓存吧！”（极其重要，配合缓存机制使用）。
*   **4xx（客户端错误）：**
    * `400 Bad Request`：请求格式错误，服务器看不懂。
    * `401 Unauthorized`：**未认证**。需要提供身份凭证（比如没登录就访问需要权限的 API）。
    * `403 Forbidden`：**被拒绝**。你虽然登录了（服务器知道你是谁），但你没有权限访问（比如普通用户试图进后台管理）。
    * `404 Not Found`：资源不存在。
*   **5xx（服务端错误）：**
    * `500 Internal Server Error`：服务器代码报错（比如代码写了 Bug，崩溃了）。
    * `502 Bad Gateway`：网关错误。通常指 Nginx 后面挂载的 Python/Java/Go 后端程序挂了，Nginx 连不上。
    * `503 Service Unavailable`：服务器超载或正在维护，暂时无法提供服务。
    * `504 Gateway Timeout`：网关超时。后端程序执行太慢（比如数据库查询超时），Nginx 等不及了。

#### 3. 响应头（Response Headers）
* `Content-Type` & `Content-Length`：同请求头，标识响应体数据的格式和长度。
* `Server`：告诉浏览器服务器用的是什么 Web 软件（如 `Nginx`, `Apache`）。
* `Set-Cookie`：服务器给浏览器发的“通行证”，浏览器收到后必须保存起来，下次请求自动带上。
* `Location`：当状态码是 301 或 302 时，指定浏览器要跳转去的**新 URL 地址**。
* `Cache-Control`：控制浏览器的缓存策略。

#### 4. 响应体（Response Body）
返回给浏览器的实际内容。如果是访问网页，这里面就是 HTML 代码；如果是请求接口，这里面通常是 JSON 数据。

### 五、 深入思考：HTTP/1.1 的纯文本设计有什么优缺点？

通过看上面两个原始报文，你会发现 HTTP/1.1 非常易读。
* **优点：** 极其友好，开发者用抓包工具一眼就能看懂数据对不对，调试非常方便。
* **缺点：** **传输效率低**。
  * 文本格式占用的体积大。
  * 每次请求都要重复发送长长的英文 Header（比如一成不变的 `User-Agent`），浪费带宽。
  * *（这也正是为什么后来的 **HTTP/2 引入了二进制分帧和 HPACK 头部压缩** 的根本原因。）*

### 一、 连接管理：短连接 vs 长连接

HTTP/1.1 的底层基于 TCP 协议，网络数据的收发依赖于 TCP 连接。

```text
短连接 (HTTP/1.0 默认)
Client      Server
  |---SYN--->|   (TCP 建立连接)
  |<--ACK----|
  |--Request->|  (HTTP 请求)
  |<-Response|   (HTTP 响应)
  |<--FIN----|   (TCP 断开连接)
  *每次请求都要经历一次完整的三次握手和四次挥手*

长连接 (HTTP/1.1 默认)
Client      Server
  |---SYN--->|   (TCP 建立连接)
  |<--ACK----|
  |--Request1>|  (HTTP 请求 1)
  |<-Response1|  (HTTP 响应 1)
  |--Request2>|  (HTTP 请求 2)
  |<-Response2|  (HTTP 响应 2) (连接保持，直接复用)
  |<--FIN----|   (空闲超时或主动断开)
```

#### 1. 短连接（Short Connection）
* **机制**：每个 HTTP 请求/响应周期都独占一个全新的 TCP 连接。请求结束，TCP 随即关闭。
* **缺点**：如果页面包含大量图片、CSS、JS 文件，浏览器需要频繁发起 TCP 三次握手和四次挥手，网络延迟高，服务器资源消耗巨大。

#### 2. 长连接（Keep-Alive / Persistent Connection）
* **机制**：在一个 TCP 连接上可以连续发送多个 HTTP 请求和响应。连接在传输结束后不会立刻关闭，而是保持空闲状态，等待后续请求复用。
* **头部控制**：
  * **启用**：`Connection: keep-alive`（HTTP/1.1 默认启用，无需显式声明）。
  * **关闭**：`Connection: close`（告知对方该请求结束后即关闭 TCP 连接）。
  * **超时限制**：服务器可通过响应头指定保持时间，如 `Keep-Alive: timeout=5, max=100`（连接保持 5 秒，最多复用 100 次）。

### 二、 缓存机制（核心重难点）

HTTP 缓存分为**强缓存**和**协商缓存**，目的是减少网络传输，提升加载速度。

#### 1. 强缓存
不需要向服务器发送请求，直接读取浏览器本地缓存。返回状态码为 `200 OK (from disk cache)` 或 `200 OK (from memory cache)`。

##### 控制头部：
* **`Expires` (HTTP/1.0 产物)**：
  * **格式**：`Expires: Wed, 21 Oct 2026 07:28:00 GMT`。
  * **原理**：使用服务器返回的**绝对时间**。如果客户端本地时间小于该时间，则命中缓存。
  * **缺点**：严重依赖客户端本地时间。如果客户端时间不准，缓存控制会失效。
* **`Cache-Control` (HTTP/1.1 引入，优先级高)**：
  * **格式**：`Cache-Control: max-age=3600`。
  * **原理**：使用**相对时间**（单位：秒）。代表资源自下载后 3600 秒内有效，不依赖客户端绝对时间。
  * **常用指令**：
    * `max-age=<seconds>`：缓存的最大有效时间。
    * `no-cache`：**不直接使用强缓存**，每次必须向服务器发起协商缓存校验。
    * `no-store`：**禁止任何缓存**（既不强缓存，也不协商缓存），每次都下载完整资源。
    * `private`：仅浏览器（客户端）可缓存，中间代理/CDN 不能缓存。
    * `public`：客户端和 CDN/代理服务器均可缓存。

#### 2. 协商缓存
强缓存失效（过期）后，浏览器携带缓存标识向服务器发起请求，由服务器决定是否继续使用本地缓存。

* **缓存未修改**：服务器返回 `304 Not Modified`（响应体为空），浏览器直接使用本地缓存。
* **缓存已修改**：服务器返回 `200 OK`，并附带最新的资源内容和新的缓存标识。

##### 控制对组：
* **第一组：基于时间戳（精度为秒）**
  * `Last-Modified`（响应头）：服务器告知该资源的最后修改时间。
  * `If-Modified-Since`（请求头）：浏览器再次请求时，将上次收到的 `Last-Modified` 值发送给服务器。服务器对比如果文件未被修改，则返回 304。
  * **缺点**：如果文件内容没变但修改时间变了，会导致缓存失效；时间精度只到秒级，无法应对一秒内多次修改的场景。
* **第二组：基于唯一标识（精度最高，优先级高）**
  * `ETag`（响应头）：服务器根据文件内容生成的唯一哈希值（只要内容变，哈希值就变）。
  * `If-None-Match`（请求头）：浏览器再次请求时发送该哈希值。服务器对比后一致则返回 304。

#### 3. 缓存决策树
```text
                  开始请求资源
                      |
              是否有本地缓存？ ---> 否 ---> 向服务器发起请求
                      | 是
             Cache-Control/Expires
                 是否过期？  ---> 否 ---> 读取本地缓存 (200 from cache)
                      | 是
               向服务器发起协商请求
        (带上 If-None-Match 和/或 If-Modified-Since)
                      |
               服务器比对标识
                 是否一致？ ---> 是 ---> 返回 304 ---> 读取本地缓存
                      | 否
               返回 200 + 新资源 + 更新本地缓存
```

### 三、 内容协商

内容协商机制允许客户端与服务端协商最适合当前客户端的资源表现形式（如语言、压缩格式、文档类型）。

#### 相关请求头（客户端期望）与响应头（服务端确定）：

| 协商维度     | 客户端请求头 (Accept)                 | 服务端响应头 (Content)           | 说明                                       |
| :----------- | :------------------------------------ | :------------------------------- | :----------------------------------------- |
| **媒体类型** | `Accept: text/html, application/json` | `Content-Type: application/json` | 客户端期望的数据格式。                     |
| **压缩算法** | `Accept-Encoding: gzip, deflate, br`  | `Content-Encoding: br`           | 客户端支持的无损压缩格式。                 |
| **语言**     | `Accept-Language: zh-CN, zh;q=0.9`    | `Content-Language: zh-CN`        | 客户端期望的语言环境（q 代表权重优先级）。 |

### 四、 会话与认证机制

HTTP 协议是无状态的，必须引入认证机制来识别用户身份。

#### 1. Cookie 与 Session 机制（传统）
* **原理流程**：
  1. **登录**：客户端向服务端提交账号密码。
  2. **创建 Session**：服务端验证通过，在服务器内存/数据库中创建一个 Session 会话，生成一个唯一的 `SessionID`。
  3. **下发 Cookie**：服务端在响应头中加入 `Set-Cookie: SESSION_ID=xyz123; HttpOnly; Secure`。
  4. **自动携带**：浏览器收到响应后存储该 Cookie。此后，每次向该域发送 HTTP 请求时，浏览器会**自动在请求头**中携带 `Cookie: SESSION_ID=xyz123`。
  5. **身份识别**：服务端读取 `Cookie` 中的 `SessionID`，查找到对应的 Session 数据，恢复用户状态。

#### 2. Token 认证（以 JWT 为代表的现代机制）
* **原理流程**：
  1. **登录**：客户端提交登录凭证。
  2. **生成 Token**：服务端验证成功，将用户信息（如用户 ID、权限）放入 JSON 对象，并使用密钥和签名算法生成一段加密字符串，即 **Token（通常为 JWT）**。**服务端不保存该 Token（无状态化）**。
  3. **下发 Token**：服务端直接将 Token 放在响应体（JSON）中返给客户端。
  4. **手动存储与发送**：客户端收到后手动将其存入 `localStorage` 或 `sessionStorage`。后续请求时，客户端必须**手动**在请求头中添加 Token：
     * 格式：`Authorization: Bearer <Your_Token_String>`
  5. **验证鉴权**：服务端收到请求后，不需要查数据库或内存，直接使用本地密钥对 Token 进行签名验证，通过则允许访问。

### 五、 范围请求（Range Requests）

范围请求支持只请求资源的一部分，常用于大文件断点续传、多线程下载和音视频在线播放。

#### 机制与头部：
* **服务器声明支持**：
  * 响应头：`Accept-Ranges: bytes`（告知客户端支持按字节范围请求）。
* **客户端请求指定区间**：
  * 请求头：`Range: bytes=0-499`（请求前 500 字节）。
  * 请求头：`Range: bytes=500-`（请求从第 500 字节到文件末尾）。
* **服务端响应分片数据**：
  * **状态码**：`206 Partial Content`（表示成功返回部分内容）。
  * 响应头：`Content-Range: bytes 0-499/10000`（当前返回的数据区间/文件总大小）。

### 六、 HTTP/1.1 的性能瓶颈

虽然 HTTP/1.1 相比 1.0 引入了长连接、缓存等大量优化，但随着 Web 应用复杂度的爆炸式增长，其固有的设计瓶颈逐渐暴露：

#### 1. 应用层队头阻塞（Head-of-Line Blocking）
在一条 TCP 连接上，HTTP/1.1 规定请求的发送和响应的接收必须是**严格串行**（按顺序 FIFO）的。
* **现象**：如果请求 1 遭遇服务器处理卡顿，后续的请求 2、请求 3 将会被卡在同一条 TCP 连接中排队等待，无法发送和接收。

```text
HTTP/1.1 队头阻塞示例：
[Client] -----> Request1 (请求大图) -------------> [Server]
[Client] -----> Request2 (请求小图标) (被阻塞等待) -> [Server]
*必须等待 Response1 返回后，才能开始处理并返回 Response2*
```

#### 2. 建立多个 TCP 连接的系统开销
为了绕过单条连接的队头阻塞，现代浏览器通常允许针对同一个域名同时开启 **6 个 TCP 连接** 进行并发传输。
* **代价**：每个连接都要进行三次握手和慢启动，增加了服务器的并发维护开销和网络带宽的瞬间损耗。

#### 3. 头部冗余（Header Overkill）
HTTP/1.1 的 Header 采用纯文本编码，且不支持压缩。每次请求都要重复携带大量的 Header 信息（如几十字节甚至上百字节的 `User-Agent`、`Cookie`），在小请求、高频发的移动网络环境下造成了极大的带宽浪费。

### 一、 设计目标

HTTP/2 的核心设计目标是在**完全不改变 HTTP 语义**的前提下，突破 HTTP/1.1 的性能瓶颈。

* **语义兼容**：HTTP/2 没有修改任何应用层概念。所有的 HTTP 方法（GET, POST）、状态码（200, 404）、URI 以及首部字段（Headers）在语义上保持 100% 一致。
* **传输重构**：HTTP/2 彻底重构了底层的传输交互机制，将原本明文的、串行的传输，升级为二进制的、并行的传输。

---

### 二、 核心特性

#### 1. 二进制分帧（Binary Framing）—— 传输的基石
HTTP/2 不再像 HTTP/1.x 那样解析明文文本，而是将所有传输信息分割为更小的**二进制帧（Frame）**。

```text
HTTP/1.1 (纯文本)  ----->  "GET /index.html HTTP/1.1\r\nHost: ..." (整块文本)

HTTP/2 (二进制帧)  ----->  [帧头 (9 字节)] + [帧负载 (二进制内容)]
```

为了实现并行传输，HTTP/2 引入了四个层级概念：
* **连接（Connection）**：一个单一的、建立好的 TCP 连接。
* **流（Stream）**：连接中的一个虚拟双向通道，承载着双向传输的帧。每个流都有一个唯一的整数 **Stream ID**。
* **消息（Message）**：对应一次完整的 HTTP 请求或响应（如一次 GET 请求或一次 200 OK 响应），由一个或多个帧组成。
* **帧（Frame）**：最小的传输单位。
  * **Headers 帧**：用于携带 HTTP 头部信息。
  * **Data 帧**：用于携带请求体或响应体的数据内容。

#### 2. 多路复用（Multiplexing）—— 解决应用层队头阻塞
得益于二进制分帧，HTTP/2 可以在**单条 TCP 连接**上同时交错传输多个请求和响应的帧，不需要像 HTTP/1.1 那样串行等待。

```text
HTTP/1.1 (串行排队):
[连接 1] --> 发送 Request1 --------------------> 接收 Response1
[连接 1] --------------------------------------> 才能发送 Request2 (队头阻塞)

HTTP/2 (交错多路复用):
[单连接] --> [Stream 1: Headers帧] -> [Stream 3: Headers帧] -> [Stream 1: Data帧] -> [Stream 3: Data帧]
*不同请求的帧根据自身的 Stream ID 在对端进行重组，互不干扰*
```
* **效果**：彻底消除了 HTTP/1.1 的**应用层队头阻塞**。浏览器只需要与同一个域名建立 **1 条 TCP 连接**，即可实现极高的并发传输，节省了服务器的端口和连接资源。

#### 3. 头部压缩（HPACK）—— 解决头部冗余
HTTP/1.x 的首部字段大且重复。HTTP/2 引入了 **HPACK** 算法进行高比例压缩。

* **工作原理**：
  1. **静态表（Static Table）**：预先定义了一个包含 61 个高频 Header 的表格（如 `:method: GET` 序号为 2，`:status: 200` 序号为 8）。传输时，直接发送对应的**索引号**代替整串英文文本。
  2. **动态表（Dynamic Table）**：连接建立后，双方在内存中动态维护一张表。如果传输了自定义 Header（如 `Authorization: Bearer abc`），它会被加入动态表。后续请求再次携带该首部时，只需发送对应的索引号即可。
  3. **哈夫曼编码（Huffman Coding）**：对于无法用索引表示的动态字符串，使用哈夫曼编码进行压缩后再传输。

#### 4. 服务器推送（Server Push）及现代演进
* **原本设计**：当客户端请求 `index.html` 时，服务器预测客户端后续必然需要 `style.css` 和 `main.js`，于是主动将这些资源提前推送到客户端的浏览器缓存中，省去了客户端解析 HTML 后再次发起请求的 RTT（往返时延）。
* **现代实践注脚**：在实际生产中，服务器推送遇到了**带宽浪费**（服务器无法精准获知客户端是否已有该缓存）以及**实现复杂**等问题。
  * **现状**：主流浏览器（如 Chrome 106+、Firefox 132+ 等）已默认**禁用并移除了对 HTTP/2 Server Push 的支持**。
  * **替代方案**：现代 Web 优化全面转向使用 **`103 Early Hints`** 状态码或 `<link rel="preload">` 指令，改由浏览器主导资源的预加载。

### 三、 局限性：传输层队头阻塞

尽管 HTTP/2 解决了应用层的队头阻塞，但它依然留有一个重大的底层性能瓶颈：**传输层队头阻塞**。

* **根源**：HTTP/2 运行在 **TCP 协议** 之上。TCP 必须保证数据的绝对有序性和可靠性。
* **瓶颈场景**：在单条 TCP 连接中，如果发生了网络丢包，TCP 协议栈会强行**暂停**后续所有已到达数据的交付，直到丢包被重新传回并确认。
* **后果**：即使丢失的只是流 1（Stream 1）的一个 Data 帧，与之毫无关联的流 3（Stream 3）的数据也会被一并卡在操作系统的 TCP 缓冲区中无法提交给应用层。丢包率高时，HTTP/2 的性能甚至不如开启了 6 个连接的 HTTP/1.1。

### 一、 设计动机

HTTP/2 虽然大幅提升了传输效率，但在极端网络环境下（如移动网络抖动、高丢包率），其底层 TCP 的硬伤成为了无法突破的瓶颈。

#### 1. 摆脱 TCP 的历史包袱
* **内核锁死（Ossification）**：TCP 协议栈由操作系统内核实现。这意味着修改 TCP 的核心特性需要用户升级操作系统，这在全球数十亿台设备上面临极其高昂的时间成本。
* **中间设备固化**：防火墙、路由器等网络设备只认识经典的 TCP 标志位，任何对 TCP 报文格式的微调都可能导致数据包被拦截丢弃。

#### 2. 彻底解决传输层队头阻塞
只要底层依赖 TCP，丢包时 TCP 的有序接收机制（Sliding Window）就会强行阻塞整条连接。HTTP/3 的目标是**将多路复用直接下沉至传输层**，彻底终结这一顽疾。

---

### 二、 核心特性：基于 QUIC 协议

HTTP/3 弃用了 TCP，将其替换为在用户空间实现的、基于 UDP 的全新传输协议——**QUIC（快速 UDP 互联网连接）**。

#### 1. 协议栈对比

| 协议层级   | HTTP/2 协议栈 | HTTP/3 协议栈            |
| :--------- | :------------ | :----------------------- |
| **应用层** | HTTP/2        | **HTTP/3**               |
| **安全层** | TLS 1.2 / 1.3 | **QUIC（内置 TLS 1.3）** |
| **传输层** | TCP           | **UDP**                  |
| **网络层** | IP            | IP                       |

*（注：QUIC 协议运行在用户态，升级和迭代只需更新应用程序/浏览器，无需升级操作系统内核。）*

#### 2. 内置加密：TLS 1.3 合并握手
在传统的 TCP + TLS 模式下，建立安全连接需要多步握手，带来明显的网络延迟：

```text
传统的 TCP + TLS 1.3 握手 (1 + 1 = 2 RTT)：
[Client] -------- TCP SYN --------> [Server]  \  TCP 握手 (1 RTT)
[Client] <----- TCP SYN/ACK ------- [Server]  /
[Client] ------ TLS ClientHello ---> [Server]  \  TLS 握手 (1 RTT)
[Client] <----- TLS ServerHello ---- [Server]  /  (建立安全连接)

HTTP/3 的 QUIC 1-RTT 合并握手 (1 RTT)：
[Client] ---- QUIC ClientHello (带上密钥协商) ----> [Server]  \  安全连接
[Client] <--- QUIC ServerHello (确认连接+密钥) ---- [Server]  /  一步到位！
```

* **极致速连**：第一次建连只需 **1 RTT**；如果之前建立过连接，可通过 Session Ticket 实现 **0 RTT** 瞬间发送应用数据。
* **高安全性**：加密不再是可选的“外挂”机制。QUIC 头部和传输控制信息在 UDP 载荷中都是被完全加密的，外界极难监听或篡改传输状态。

#### 3. 解决传输层队头阻塞：独立流设计
QUIC 在底层的 UDP 报文中，将“多路复用”作为原生属性实现：

* **机制**：QUIC 的 UDP 数据包里包含 `Stream ID` 和 `Offset`（偏移量）。
* **效果**：不同 Stream（流）之间在传输层上没有任何依赖关系。如果 Stream 1 的包在传输中丢失，传输层仅仅会暂停 Stream 1 对应数据的递交并等待重传。**Stream 2 和 Stream 3 的数据包如果安全到达，操作系统会直接交付给应用层（HTTP/3）处理**，彻底阻断了全局阻塞现象。

#### 4. 连接迁移（Connection Migration）
* **TCP 的局限**：TCP 连接依赖四元组：`(源 IP, 源端口, 目的 IP, 目的端口)`。当用户走出家门，手机从 Wi-Fi 自动切换到 5G 移动网络时，客户端 IP 发生改变，旧的 TCP 连接瞬间断开，所有下载和请求被迫中断，必须重新进行 TCP 三次握手和 TLS 协商。
* **QUIC 的创新**：QUIC 不使用四元组识别连接，而是引入了一个独一无二的 **64 位/128 位 Connection ID（连接 ID）**。
  * **机制**：无论手机的 IP 地址和端口号怎么变，只要发送的 UDP 报文中依然携带原先的 `Connection ID`，服务器就能瞬间认出这个客户端，并无缝延续旧会话。
  * **效果**：网络无缝切换，用户完全感知不到任何重连延迟或卡顿。
